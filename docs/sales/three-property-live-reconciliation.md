### How the working address would flow under checked-in main

1. `app/clearwater/resident-shell.tsx` accepts/normalizes the address and offers suggestions via `search_trusted_municipality_addresses` (CLEAN + Clearwater only). Selection is confirmation, not authority to evaluate.
2. `app/clearwater/property-resolution.ts` invokes informational `resolve_property_address_state`, then independently calls `find_trusted_property_by_address` through `lib/properties/lookup.ts`. Both must agree on one active canonical match. REVIEW, ambiguity, no-match and unconfirmed/outside jurisdiction stop the flow.
3. `lib/properties/jurisdiction.ts` requires CLEAN and jurisdiction key `clearwater`. `facts.ts` emits only `property.zoning_district` from the stored normalized code. There is no separate project-readiness or overlay-absence check here.
4. `app/clearwater/fence/actions.ts` adds `project.structure_type='fence'`, `project.work_type='new'`, `project.temporary_construction_fence=false`; `lib/rules/{index,loader,evaluate}.ts` fetch and evaluate live published content. Material, fence line, frontage, height and site restrictions remain unknown unless separately supplied; this resident flow does not collect them.
5. `lib/guides/fence.ts` constructs information cards, including reference outcomes from UNKNOWN/nonmatched buckets; `fence/workflow.tsx` renders them and permit/referral links. Backend citations may lack URLs and therefore be invisible in the existing UI. A rendered four/six-foot card is not evidence of a verified project entitlement.

This trace explains the repository path, not the actual deployed implementation of 1975. Record deployed SHA first; an older or modified deployment could have a different resolver path. The disabled `/` form remains hardcoded in main and is independent of database recovery; use the confirmed resident route for smoke testing without changing deployment in this task.

### Idempotency contract for later implementation

- Join on jurisdiction + canonical parcel identity and source address identity **and** active normalized address; a match on only one key is a conflict, not permission to overwrite. Serialize one reviewed batch; transaction locks plus existing unique constraints protect races. Concurrent unexpected conflicts abort/replan, never `ON CONFLICT DO UPDATE` over source facts.
- **REUSE:** all expected evidence/QA/base/jurisdiction/identities match. Leave existing rows and `updated_at` unchanged. Use a versioned external cohort manifest to avoid unnecessary metadata writes. If provenance must be attached, add only a namespaced versioned entry with an expected-before guard, preserving every existing JSON key.
- **INSERT_ADDRESS:** the existing parcel is independently verified and its QA/evidence agrees; only the precise missing address link is created. Hold inactive/alias/ambiguous/conflicting matches for owner review. No permission propagates to sibling addresses.
- **INSERT_PROPERTY_AND_ADDRESS:** only a verified, originally CLEAN ordinary LMDR source case with absent canonical identities; create one property and one exact address link, recording source snapshots, review and batch provenance. Unknown source identity or original REVIEW is HOLD, not a new CLEAN row.
- **HOLD:** raw code, source version, QA, any known human exception, jurisdiction, overlay/additional-district evidence, ownership/project scope or identity disagrees. Do not repair classification to make the demo pass; choose another explicitly approved case.
- A second application of the same reviewed batch is a **true no-op**: zero new rows, zero metadata changes and zero timestamp churn. Same batch ID with changed content/evidence aborts and needs a new reviewed version. Rechecking a later source does not silently inherit the earlier decision.

## Exact non-destructive rollback contract

Prepare and approve rollback **before** any later data application. Store the batch manifest/hash, inserted row IDs, expected post-images and targeted before-images privately with the owner, not in Git. Reconfirm the private backups' coverage and restore limitations; do not ask the owner to transfer them.

1. On failure, first remove the affected identities from the server-side pilot allowlist (or disable fence evaluation with a referral). This requires separately authorized app release if needed; database recovery is not the first response to a card defect. Preserve the original working anchor unless its own guidance is unsafe.
2. For **REUSE/no-write** rows, database rollback is a no-op. Do not disable their pre-existing active address links or change their zoning/QA.
3. For newly inserted links, a separately reviewed compensating **forward** transaction sets `active=false` only for recorded batch-owned address IDs whose current post-image and dependencies still match. Retain the new property and all source evidence; mark the batch withdrawn in its own namespace if used. Do not delete a property, cascade-delete links or deactivate unrelated sibling addresses. An approval namespace alone is insufficient: exact inserted IDs are required.
4. For a namespaced metadata addition on an existing row, compare current after-image with the recorded expected one. Restore only the affected namespace's prior value (or remove only the key that this batch added); preserve other metadata, IDs, raw classification and QA. If another actor changed the same key or introduced dependencies, abort and review rather than overwrite. A second compensation is a no-op; an existing inactive link is not blindly reactivated.
5. Validate the original anchor, pre-existing rows, source/approval fingerprints and expected active-link counts. Record a withdrawn batch so an accidental rerun cannot reactivate it without a new explicit decision. Never edit migration history, rerun historic enrichments or perform a database reset.
6. If before-images are unavailable/corrupted, stop further mutations. Owner locally verifies archive readability, PostgreSQL compatibility, role/extension prerequisites, completeness and restoration order for the private schema/data/roles exports. A real restore rehearsal requires a separately authorized isolated nonproduction target; compare restored constraints/RLS/RPCs/counts/three identities there. It may also require platform-managed roles and Storage object backups, not just those SQL files. No automatic concatenation, restore into production or role overwrite is authorized. Use the rehearsed copy to derive a narrow forward repair; any production restore/recreation is a separate owner decision.
