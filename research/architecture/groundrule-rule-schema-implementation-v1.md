# Groundrule Rule Schema Implementation v1

## Implementation status

This implementation adds the smallest database-only version of the approved
Groundrule generalized municipal rule schema. It contains no jurisdiction, project,
input, source, provision, or rule seed data and makes no application or UI changes.

The migration is:

`supabase/migrations/20260822000000_create_municipal_rule_schema.sql`

## Tables implemented

The migration creates all 13 MVP tables from the approved architecture:

1. `jurisdictions` — generalized authorities with optional parentage.
2. `project_types` — reusable project taxonomy.
3. `rule_sets` — jurisdiction/project coverage and publication packages.
4. `regulatory_sources` — authoritative document editions.
5. `source_provisions` — addressable, citable parts of a source.
6. `rules` — stable legal-proposition identities and active-version pointers.
7. `rule_versions` — versioned conditions, research/runtime states, and effective
   intervals.
8. `rule_outcomes` — ordered structured findings produced by a version.
9. `input_definitions` — reusable typed facts.
10. `input_options` — global or jurisdiction-scoped enum values.
11. `rule_version_inputs` — declared applicability/compliance/context/output input
    manifest.
12. `rule_citations` — version-to-provision provenance.
13. `rule_relationships` — directed exceptions, dependencies, specificity, and
    unresolved-conflict links.

All entity keys are UUIDs generated by `gen_random_uuid()`. The two manifest/link
tables use the approved composite primary keys. Research rows include creation and
update timestamps, and a shared trigger maintains `updated_at`.

## Relationships

```text
jurisdictions 1---* rule_sets *---1 project_types
      |                  |
      |                  1
      |                  * rules 1---* rule_versions 1---* rule_outcomes
      |                            |          |
      |                            |          * rule_version_inputs *---1 input_definitions
      |                            |
      |                            +--- rule_relationships ---+
      |                                                     rules
      |
      +---* regulatory_sources 1---* source_provisions
                                         |
rule_versions *---* source_provisions via rule_citations

input_definitions 1---* input_options *---0..1 jurisdictions
```

Foreign keys use restrictive deletion so published or referenced regulatory history
cannot be removed accidentally. The circular `rules.active_version_id` reference is
added after `rule_versions` and is deferred; a deferred constraint trigger confirms
that it points to a published active version of the same rule.

## Constraints and controlled values

Constrained `text` is used instead of PostgreSQL enums. This follows the
architecture's maintainability recommendation: adding a controlled value requires a
reviewed check-constraint migration rather than replacing an enum type. Checks cover
jurisdiction and source types; research, coverage, lifecycle, and evaluation states;
input data/source/scope types; input roles and authority requirements; outcome and
severity types; citation roles; and the five MVP relationship types.

Other integrity controls include:

* stable-key formats and uniqueness at the appropriate global or parent scope;
* proper half-open effective-date intervals (`effective_to > effective_from`);
* verified status, verification time, publication time, and effective start before a
  rule version may be active;
* exclusion of overlapping published active intervals for the same rule;
* a deferred publication check requiring an outcome and primary citation;
* an immutable-published-version trigger, with only the controlled transition from
  active to superseded and closure of its effective interval allowed;
* immutable outcomes, input manifests, and citations after their version publishes;
* input options restricted to enum definitions with matching global/jurisdiction
  scope;
* subject inputs required for numeric/range/required-value outcomes; and
* non-self-referential, justified/cited, uniquely active rule relationships.

An input declaration's parity with condition facts/outcome subjects, semantic JSON
operand compatibility, relationship cycles, and version-constrained relationship
metadata remain publication-validator responsibilities. Those checks require
cross-row/application context and are intentionally not hidden in SQL.

## Indexes

Indexes are limited to approved MVP access paths:

* jurisdiction/project/research/effective lookup and a partial published rule-set
  lookup;
* source jurisdiction/type/effective lookup and source identity/checksum uniqueness;
* rule-set keys, legacy keys, and non-null group keys;
* active published rule-version effective lookup plus the no-overlap exclusion;
* global and jurisdiction-scoped option uniqueness and scope lookup;
* reverse input-to-version and provision-to-version lookup;
* relationship traversal in both directions and effective-date lookup; and
* active input-definition discovery.

No condition GIN or provision full-text index is included because the approved
architecture says those require evidence from later query/research workloads.

## JSONB validation boundary

The database validates that JSONB metadata/validation/parameter columns contain the
expected top-level object or array. `groundrule_valid_expression` recursively checks
the MVP condition AST's node shape, allows only the approved MVP operators, rejects
mixed/unknown node keys, requires non-empty Boolean groups, and checks the basic
operand containers for comparisons. It is used for both rule conditions and optional
relationship scope conditions.

Application-level publication validation must still enforce:

* fact keys exist and exactly match `rule_version_inputs` declarations;
* operators and literal values match the referenced input's data type and unit;
* enum literals exist in the correct global or jurisdiction option scope;
* `validation` matches the input type (including JSON schema and geometry details);
* every outcome's `parameters` has the type-specific shape and valid units/tokens;
* outcome subjects are present in the manifest;
* relationship metadata/version constraints are valid and semantic dependency
  cycles do not exist;
* citation/source consistency and any licensing constraints; and
* message-template interpolation uses only allowlisted tokens.

This deliberately avoids implementing a PostgreSQL JSON Schema engine or a rule
evaluator.

## Row level security

RLS is enabled on every new table. Anonymous and authenticated clients may select
only public reference content: active taxonomy rows, verified published rule sets,
their published active rules/versions and children, cited sources/provisions, and
relationships between published active rules. Research notes on drafts and inactive
content are therefore not public.

There are no client write policies. Anonymous and ordinary authenticated clients
cannot insert, update, or delete regulatory content. MVP authoring must use trusted
service-role/server administration or a direct database connection, both of which
bypass RLS. No authentication model or speculative researcher-role table was added.

## Existing municipalities compatibility

The migration deliberately does not rename, alter, copy, delete, add RLS to, or
replace `public.municipalities`. The existing application query of
`municipalities(name,state)` filtered by `slug` remains unchanged. The new
`jurisdictions` table coexists with it as the generalized rule-schema authority
table. Reconciliation/backfill can occur in a separate reviewed content migration;
this avoids guessing the remote table's unversioned constraints or identifiers and
avoids altering existing municipality data.

## Deviations and implementation clarifications

There are no architectural model deviations. These concrete choices resolve places
where the approved document allowed implementation judgment:

* Controlled text checks are used instead of PostgreSQL enums.
* `lifecycle_status` is explicit on `rule_versions` to represent the approved
  runtime active/superseded/withdrawn axis.
* `source_metadata` is provided for varying document metadata, while jurisdiction
  reference/boundary metadata is stored in `reference_metadata`; neither adds GIS.
* `known_gaps` is a JSON array so limited coverage can enumerate gaps without a
  separate later-workflow table.
* `btree_gist` supports a database-enforced exclusion constraint for active interval
  overlap. Supabase supports extensions in its `extensions` schema.
* The database enforces feasible JSON shapes and publication invariants. The broader
  generic TypeScript content validator and synthetic evaluator fixtures described as
  the next architecture sequence are intentionally not included because this task is
  database structure only.

## Intentionally unimplemented

No Clearwater or mock content, content ingestion, evaluator, persisted projects or
facts, answer/evaluation snapshots, GIS/PostGIS data, derivation lineage, source
object storage, authentication, researcher workflow/audit-event tables, generated
TypeScript database types, or UI/application behavior is included. The repository
does not maintain generated Supabase database types today; generate and commit them
only when the team establishes that workflow after applying the migration.

## Manual Supabase application steps

After merge, apply the migration safely as follows:

1. Create a database backup or Supabase point-in-time recovery checkpoint and note
   the target project's current migration state.
2. Review the SQL in
   `supabase/migrations/20260822000000_create_municipal_rule_schema.sql`, especially
   the `btree_gist` extension, RLS policies, and the explicit absence of operations
   on `public.municipalities`.
3. Link the Supabase CLI to the intended project in a trusted local/CI environment;
   do not place a service-role key in the browser or repository.
4. Run `supabase db push --dry-run --linked` and confirm that only this migration is
   pending and no destructive diff is reported.
5. Run `supabase db push --linked` during a controlled deployment window.
6. Verify all 13 new tables have RLS enabled, anonymous reads expose no unpublished
   rows, anonymous writes fail, and the existing municipality page/query still reads
   `public.municipalities` successfully.
7. Generate TypeScript database types from the applied project if/when generated
   types become part of the repository workflow; do not hand-maintain a fabricated
   generated file.
8. Add content only through a later reviewed migration/import after the generic
   publisher validator and synthetic fixtures exist. Do not activate Clearwater
   candidates as part of applying this schema.
